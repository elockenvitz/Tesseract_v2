  See "Stage 3 gate" below.

## Why one build

`scripts/netlify-should-build.mjs` builds unconditionally when
`CONTEXT=production` or `BRANCH=main`. Every push to main is one production
build, so four PRs merged one at a time would cost four. Batching into a single
release branch and landing it as one PR costs one.

Do not put `[preview]` in any commit message or PR title on this branch — that
is the opt-in that would produce an additional deploy preview build.

## ⚠️ Migration replay hazard — read before touching the database

`supabase/migrations/20260828090000_coverage_trigger_tenant_scope.sql` is a
faithful record of a migration that was applied to production by hand on
2026-08-28. Its presence in the repo is correct: it is the source-control
reconciliation this release exists partly to perform, and it was verified
against production before merging — applying it to a scratch transaction
reproduces production's live `end_previous_coverage()` and `log_coverage_change()`
byte for byte.

**It must never be manually replayed once Stage 3 is live.**

It does `CREATE OR REPLACE FUNCTION` on both trigger functions with bodies that
contain **zero** references to `coverage_scope` — they predate the column. Stage
3's `20260828110100` re-adds four lane/owner predicates to those same two
functions. So running `090000` again, after Stage 3 has been applied, silently
replaces the lane-aware bodies with lane-blind ones and reopens exactly the
mixed-lane defects Stage 3 exists to close:

- an org assignment retiring colleagues' personal declarations, and
- `coverage_history` attributing one person's declaration to another.

Nothing warns you. The functions still exist, the triggers still fire, and the
damage only shows up in retired rows and a wrong audit trail.

**An in-order replay into a fresh environment is safe.** The filename timestamps
are monotonic —

```
20260828090000_coverage_trigger_tenant_scope.sql        lane-blind bodies
20260828110000_coverage_scope_and_self_service_rls.sql  adds coverage_scope
20260828110100_coverage_triggers_scope_aware.sql        lane-aware bodies  ← wins
```

— so a runner that applies every file in order converges on the lane-aware
definitions. The hazard is **selective or out-of-order replay of `090000` alone**
against a database that already has Stage 3.

This is deliberately not solved by editing `090000`. Rewriting a migration to
describe something other than what was applied would make the file lie about
production, which is the problem the reconciliation is meant to fix. The
protection is operational: no replays, ever, against production.

Also note production's migration ledger does not describe production (see
`docs/` on schema drift). Query the live database before asserting anything
about a deployed policy, column or function.

## Deploy sequence

### 1. Merge the release PR
One PR, `release/2026-08-28-batch` → `main`. Merging it produces the single
production build. PRs #215 and #216 close automatically — their commits are in
the merge.

### 2. Smoke the live site

**Stage 3 gate — these three must pass before any database work:**

1. **CSV coverage import** stamps `organization_id`. Import one or two rows,
   then confirm `select count(*) from coverage where organization_id is null`
   is still **0**.
2. **Coverage gaps bulk assign** stamps `organization_id`. Same check.
3. With no workspace resolvable, both paths **refuse** rather than writing.

**Regression checks:**

4. Charts — desktop panel opens without throwing; touch interaction intact.
5. Quick Thoughts — feed loads, org-scoped, no cross-tenant rows.
6. Signup/Invite — `/invite/:token` renders; a valid invitation opened by the
   *wrong* signed-in account shows "Wrong account" and does not trap the browser
   in a redirect loop; sign out and switch account works.
7. Email verification inert — a signup returns a session immediately and never
   shows the "Confirm your email" waiting room.
8. Ideas — snooze and dismiss persist; feed filters correctly.
9. Coverage manager — existing admin CRUD unchanged.
10. Console clean; no new Sentry error class.

### 3. Make "Invite entry" a required check

Only **after** this batch is on main, because the job does not exist on main
until then. Requiring it earlier blocks every PR from a main-based branch,
including hotfixes, for no benefit.

```
Settings → Branches → main → Require status checks → add "Invite entry"
```

Current required checks: `Unit tests`, `Card layout`, `Type check (cards)`.

### 4. Coverage Stage 3 migrations — only after the gate passes

The gate is *deployed and verified*, not merged and not built. Migration 1 adds
`organization_id NOT NULL`; if a writer path still omitted the column, that path
starts failing with `23502` the moment it lands.

Apply as one change window, with no verification pause between the two:

```
20260828110000_coverage_scope_and_self_service_rls.sql
20260828110100_coverage_triggers_scope_aware.sql     ← immediately after
```

Then verify: 34 rows / 26 active / every row `coverage_scope = 'org'` /
`organization_id` NOT NULL / 7 policies / `anon` grants 0 /
`trg_coverage_scope_immutable` and `trg_stamp_personal_coverage` present. Run
the coverage security suite against production.

If migration 2 fails after migration 1 succeeded: retry it (every statement is
`CREATE OR REPLACE` or drop-then-create). If it fails again, disarm the personal
lane by dropping the three `*_own_personal` policies — no personal rows exist
yet, so that loses nothing and returns the boundary to its pre-Stage-3 state.
Do **not** roll migration 1 back.

No `supabase db push`. No directory replay. No ledger edits.

### 5. Email verification enforcement — separate, later
Config-only, no deploy. `docs/email-verification-rollout.md` has the order.
